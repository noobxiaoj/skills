# Prototype（原型）

默认使用简体中文与用户沟通。原型说明、运行方法、结论和假设都用中文；代码、命令、路由、文件名保持项目风格。

prototype 是**用于回答问题的一次性代码**。问题决定原型形态。

## 选择分支

从用户提示、周边代码或向在线用户询问，识别正在回答的问题：

- **“这个逻辑 / 状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。构建一个小型交互式终端 app，把状态机推过那些纸面上难以推理的 case。
- **“这个应该长什么样？”** → [UI.md](UI.md)。在单一路由上生成几个差异显著的 UI 方案，用 URL search param 和浮动底栏切换。

两个分支产物非常不同，选错会浪费整个原型。如果问题确实模糊且用户不在线，就根据周边代码默认选择更匹配的分支，例如后端模块 → logic，页面或组件 → UI，并在原型顶部说明假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性代码，并明确标记。** 把 prototype code（原型代码）放在接近未来真实使用位置的地方，例如被验证模块或页面旁边，让上下文清晰；但命名必须让读者一眼看出它是 prototype，不是生产代码。一次性 UI 路由要遵循项目已有路由约定，不要发明新的顶层结构。
2. **一个命令即可运行。** 使用项目现有任务运行器支持的方式，例如 `pnpm <name>`、`python <path>`、`bun <path>`。用户必须能不费脑启动它。
3. **默认不持久化。** 状态保存在内存中。持久化是 prototype 要验证的东西，不应该成为依赖。如果问题明确涉及数据库，使用 scratch DB 或本地文件，并用清楚的 “PROTOTYPE - wipe me” 名称。
4. **跳过打磨。** 不写测试；除了让 prototype 可运行所需的错误处理，不做额外错误处理；不抽象。目标是快速学习，然后删除。
5. **显式展示状态。** 每次动作后（logic）或每次切换变体后（UI），打印或渲染完整相关状态，让用户看到变化。
6. **完成后删除或吸收。** 当 prototype 回答了问题，要么删除它，要么把已验证决策折进真实代码；不要让它长期烂在仓库里。

## 完成时

prototype 中唯一值得保留的是**答案**。把答案和它回答的问题记录到持久位置，例如 commit message、ADR、issue，或 prototype 旁边的 `NOTES.md`。如果用户在线，这可以是一段快速对话；如果不在线，留下占位，让他们或下一轮的你在删除 prototype 前补上结论。
