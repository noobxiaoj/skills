默认使用简体中文与用户沟通。问题、推荐答案、选项和阶段总结都用中文；代码、命令、文件名、专有名词保持原文。

围绕这个计划的每个方面持续追问，直到达成共同理解。沿着设计树逐个分支推进，逐一解决决策之间的依赖。每个问题都要提供你的推荐答案。

一次只问一个问题。不要一次性列出多个问题。

如果某个问题可以通过探索代码库回答，就优先探索代码库，而不是询问用户。

## 触发后的默认行为

只要本 skill 被调用，第一条回复就必须进入卡片式追问。不要先输出普通建议列表、评审列表或长段解释。

如果用户问“还有什么优化”“我来判断是否要做”“先别改代码，只评估一下”等评估型问题，也仍然使用 `追问卡片`：先确认用户最想优化的维度，再继续追问。不要因为用户在征求建议就切回普通回答。

只有在用户明确说“停止追问”“直接总结”“开始实现”“不用卡片格式”时，才退出卡片式追问。

## 严格卡片模式

本 skill 使用严格卡片模式。只要没有退出卡片式追问，每次回复只能由下面这些结构组成：

1. 可选的一句 `已记录：...`，用于复述用户上一轮选择。
2. 一个 Codex 结构化选择 UI。
3. 每 3-5 张卡片后的 `## 当前已确认` 简短状态块。
4. 用户明确要求退出时的固定总结块。

禁止输出普通建议列表、开放式头脑风暴列表、长段背景解释、寒暄或“下面是一些建议”之类的前言。即使用户问“告诉我有哪些优化”，也必须把问题改写成一张追问卡片，让用户先选择优化方向。

如果需要解释概念或权衡，只有在用户选择 `C` 或明确要求解释时才解释；解释后必须重新给出同一张追问卡片，不要跳到下一问。

## Codex 结构化选择 UI

如果当前 Codex 环境提供结构化用户输入工具，例如 `request_user_input`，必须使用它生成真正的选择 UI，而不是在聊天正文里渲染 Markdown 卡片。

如果当前环境没有结构化用户输入工具，不要退回 Markdown 表格，不要用普通文本伪装卡片。直接停止本轮追问，并用下面这句提示用户：

`当前 Codex 会话没有开放结构化选择 UI 工具，无法弹出选择框。请切换到支持结构化输入的模式后再使用 $grill-me。`

每张追问卡片映射成一个结构化问题：

- `header` 使用 12 个字符以内的中文短标题，例如 `优化方向`、`目标确认`、`边界选择`。
- `question` 写本轮唯一问题。
- `options` 提供 2-3 个互斥选项；推荐项放第一位，label 后加 `(推荐)`。
- 选项描述写清选择后的影响或取舍。
- 不要在正文里重复同一组选项；结构化 UI 已经承载选项。
- 如果工具自带 Other / 自定义输入，不要再额外添加 `D. 自定义`。

结构化选项默认使用这三类：

1. `采用推荐 (推荐)`：按我的推荐答案继续。
2. `换个方向`：用户不同意推荐方向。
3. `先解释`：先解释概念或权衡，再回到同一问题。

## 回答要求

- 用户回复 `A`、`B`、`C`、`D`、`同意`、`不同意` 或自然语言时，先用一句话复述你对用户选择的理解，再继续下一张追问卡片。
- 如果用户选择 `A`，按推荐答案记入已确认决策，然后继续追问下一个最重要分支。
- 如果用户选择 `B` 或给出不同方向，接受用户方向，不要争辩；只在明显存在风险时用一句话指出风险，然后围绕新方向继续追问。
- 如果用户选择 `C`，先解释概念或权衡，再重新给出同一张追问卡片，不要跳到下一个问题。
- 如果用户选择 `D` 或自由输入，把自由输入整理成一条已确认或待确认决策，再继续。
- 如果用户的问题其实可以通过读取代码、文档或现有上下文回答，先探索并给出发现；只有发现仍不足时才出追问卡片。
- 每 3-5 张卡片后，用 `## 当前已确认` 简短列出已确认决策和仍未解决的问题，然后继续下一张卡片。

## 退出总结格式

当用户明确说“停止追问”“直接总结”“开始实现”时，退出卡片追问，并使用固定总结格式：

```md
## 已确认决策
[列出已确认内容]

## 仍未解决
[列出未解决问题]

## 主要风险
[列出最重要风险]

## 推荐下一步
[给出下一步动作]

## 适合接力的 skill
[列出适合继续使用的 skill，如无则写“无”]
```
